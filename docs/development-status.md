## 步骤 2 开发边界

当前生产链路依赖两类显式信号识别冲突：模型返回的 `contradicts_memory_ids`，以及相同 `canonical_key`。当新旧事实缺少字面重合、模型未返回旧 ID 或 canonical key 不稳定时，冲突可能漏检。离线失败样本 `conflict-03`（“从北京搬到上海”对“目前住在北京”）用于重现这一缺口。

本步计划：

1. 先证明 `conflict-03` 是否经过与普通聊天 Worker 相同的生产候选检索与治理逻辑，避免只修改离线评分函数。
2. 在记忆服务层增加用户域、`active` 状态内的语义冲突候选检索；Graph 和 Worker 仍只负责编排，不直接修改记忆版本。
3. 新候选确认前保持旧版本 `active`；确认后旧版本变为 `superseded`，拒绝时旧版本不变，撤销时成对恢复。
4. 为目标、偏好和居住地变更补回归，并增加无关事实样本，防止语义相近但不冲突的记忆被替换。
5. 运行单元测试、离线评测、真实 PostgreSQL 集成测试和前端构建；更新基线报告及仍存在的失败说明。

## 步骤 2 完成标准

- `conflict-03` 通过生产冲突链路，不依赖测试专用分支或硬编码地点词表。
- 目标变更、偏好变更和居住地变更均生成可审计的 `pending` 新版本。
- 确认前旧版本继续参与召回；确认、拒绝和撤销行为有自动化测试。
- 无关事实不会因为语义相近被错误标记为冲突。
- 评测报告明确记录指标变化和剩余质量限制。
