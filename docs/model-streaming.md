# 对话流式生成

更新日期：2026-10-19

## 模型与界面链路

普通回答、工具调用后的回答和工具预算触顶后的总结统一通过 `app.agent.streaming.stream_model` 消费模型的 `astream()`。同步 Graph 入口使用 `stream()`。LangGraph 的 `ainvoke()` 只负责运行状态图；节点内部仍逐段消费模型输出并向服务层发送正文。

模型分片 → 后端正文合批 → 持久化运行事件 → SSE → 前端合并去重 → Markdown 渲染。首个非空正文分片立即发送；后续在收到分片时，按距上次发送至少 100ms 或累计 256 字符合批，正常结束时补发余量。该机制控制数据库提交和界面渲染频率，不模拟打字，也不等待完整回答再切片。

## 运行事件协议

| 事件 | Payload | 行为 |
| --- | --- | --- |
| `model.output.started` | `output_id` | 开始一次模型输出，重置该轮实时正文 |
| `model.output.delta` | `output_id`, `text` | 向相同输出追加正文，保留换行、缩进与 Markdown 标记 |
| `model.completed` | `answer_length` | 最终模型回复已聚合完成 |
| `run.completed` | 原有 ChatResponse，包含完整 `message` | 用最终保存的回答替换实时草稿，包含预算提示或兜底回答 |

正文事件复用 `run_id + sequence`、先提交后投递和已有事件查询接口，无需数据库迁移。前端先合并、排序、去重事件，再按 `output_id` 还原最新一次输出；新的模型轮次替换上一轮草稿，迟到的旧输出分片不追加到新回答。正文分片不逐条展示在运行事件列表中。

`AIMessageChunk` 在后端完整聚合后转为 `AIMessage`，随后才路由和执行工具。因此工具名称、调用 ID 和 JSON 参数跨分片仍能正确恢复。只将消息的可见 `.text` 转为正文事件，工具参数、推理块和供应商元数据不会作为回答流发送。内部会话摘要、后台结构化记忆提取及独立回顾接口保持原有调用方式，不混入对话正文流。

## 完成、停止与恢复

- 正常完成：完整助手消息只保存一次，异步记忆提取继续使用原有队列；最终回答覆盖实时草稿，不重复追加。
- 显式取消或模型异常：关闭上游流，保留已经投递并提交的正文事件；未成功完成的正文不保存为完整助手消息，界面显示运行终态及可恢复的部分输出。尚未发送的合批余量可能丢弃。
- 连接断开：任务继续执行。已有客户端断线恢复机制通过事件游标补取输出，不重新发起模型生成。
- 刷新页面：无完整助手消息的运行由 `ChatRun` 分页读取事件并显示部分 Markdown，继续轮询至终态；完成后重新加载最终保存的消息。

### 实际 Edge 页面复验

用户反馈仍显示“正在思考”后，在其原有 Edge 标签页复现了相同现象：后端已连续生成正文事件，旧版前端却没有消费正文增量。用户此前的贪吃蛇请求产生了 292 个正文事件，分布在约 44 秒内，排除了模型一次性返回。上一轮验证仅刷新了内嵌浏览器，遗漏了该 Edge 标签页。
